My computer science coursework helped me connect individual programming skills to a broader understanding of how software systems work. Through application development, mathematics, algorithms, testing, databases, and security, I developed a clearer picture of how design decisions affect an application’s reliability and usefulness. My goal is to become a full-stack software engineer with a focus on backend development. This portfolio demonstrates my progress toward that goal through improvements to an Animal Shelter Dashboard originally developed in CS 340.

One of the first projects I had in programming was a text-based game using Python. I liked this project because I was implementing code that I had thought up. It felt cool that I could turn my ideas into actual behavior that software had, and that made me want to learn more and more. Math classes were another way that I built my foundation. I enjoyed seeing how complex math ideas and logic applied to software engineering. I learned through doing software, but it was the education that I received that helped me understand how things worked.

Collaboration and Communication

In my work as a Senior Technical Program Manager, I regularly bridge the gap between product and engineering teams and project management and executive teams. The information people need varies by situation and individual, so effective communication requires judgment about both content and detail. Executive updates, for example, are generally high level while still providing enough information to support decisions.

This experience has helped shape how I document technical work. When a developer is reviewing an implementation, they need to know about interfaces, assumptions, failure conditions, etc. When someone is assessing the value of the work, they need to know what problem it solves, why certain decisions were made, and what the behavior is like. My portfolio uses a code review, enhancement stories, documentation, and application screenshots to communicate different levels of detail about the project. I didn't work on the dashboard with a shelter team, but I structured the code and accompanying materials so that someone else could understand, run, and review it.

Software Engineering and Problem Solving

I learned two important lessons from the capstone. First, good software design and engineering means structuring your code around well-defined responsibilities. Second, database access must be robust. I applied these lessons to improve an application in the areas of software design and engineering, algorithms and data structures, and databases. This helped me understand the impact that changes in one area of an application can have on other areas.

For the software engineering enhancement, I separated the concerns of configuration, data access, application logic, and presentation into different components. This allowed a clearer understanding of responsibilities and the ability to test behavior without the need for the initial database setup.

I replaced the rigid rescue preference categorization with configurable preference scoring and ranking algorithms. I wrote dictionaries to map rescue roles to scoring profiles, and sets to handle multiple breed matching. The algorithm properly accounts for missing information and ties, and I analyzed the additional processing time and memory required to rank candidates and store explanations. The preference scores demonstrate the degree of preference match, but do not indicate animal suitability for rescue roles.

I implemented the database improvements in SQLAlchemy and SQLite with validated queries, schema constraints, transactional operations, and pagination. This project has improved my confidence that reliability means predictable behavior on failure, such as rolling back a failed batch import, rejecting invalid records, and proper pagination to maintain meaningful ranking.

Testing and Security

I automated tests to objectively analyze these decisions. The ultimate change set passed 61 tests for application behavior, ranking, validation, and database access. Synthetic records and temporary SQLite databases were used as the original MongoDB setup was not available. These tests ensure that the local deployment is ok, but do not ensure that the deployment is production-ready or that there is a data migration for the production data.

My mindset around security has also shifted. I now believe that validating inputs, protecting credentials, and handling failures gracefully should be designed into the application from the ground up. Features such as external configuration, controlled error messages, bounded query inputs, database constraints, and transaction rollback illustrate this in the improved application.

Professional Direction

These improvements demonstrate how I relate software architecture, backend engineering, persistence, testing, and security. My portfolio demonstrates my growing engineering proficiency and my ability to communicate technical and business concepts. I aim to leverage these skills to develop clear, maintainable, and dependable software and further develop my backend engineering proficiency.
