Milestone Four Database Enhancement Narrative

Dorn Chamberlain

10/04/2026

For milestone four, I extended the Animal Shelter Dashboard by adding a relational database layer with SQLAlchemy and SQLite. This refactoring moves the database work to a portable local environment, keeping the scoring/ranking functionality from milestone three. This gives a functional means to store, retrieve, update, and delete records without the original MongoDB implementation, which was scored with a zero due to it being non-existent.

This piece of artifact should be in my ePortfolio because it directly shows how I applied database-related knowledge to the application. The previous artifacts helped to refine the application architecture and how to rank the candidates. This piece shows the effort behind the scenes to have the records persisted in the database and easily pulled to display on pages with a reasonable number of results. The repo, database constraints, query validation, and integration tests are great things to improve upon as a full-stack engineer with a focus on the back end.

One design decision was to use a shelter outcome row as a record. Each record has a required, unique ID, while the same animal ID can appear in multiple records for that animal. If animal IDs were unique, it would be impossible for an animal to have more than one record. Unknown optional fields should stay unknown rather than random guess values. The schema validates that text fields aren't too long, that ages are non-negative, and coordinates are in valid ranges. New writes will reject bad data, but constraints in the database schema offer another level of validation in case the proper validation code is bypassed.

The repository was implemented with CRUD interfaces and transactions to guarantee consistency of updates. The batch import was configured to either commit changes completely or abort (roll back) if a record did not satisfy a constraint. Updates were made without changing the record ID, and meaningful responses were provided for deleting or updating non-existent records. SQLAlchemy was used to map input values to query parameters, and the application enforced which fields could be specified for retrieving, filtering, and sorting. These could all be demonstrated locally with command-line utilities without the hassle of implementing public editing interfaces and controls on the dashboard.

The tricky part was implementing database page navigation with the ranking algorithm. If you only rank the results that are on a page, you can lose good candidates that are on a later page. The new query first scores and ranks all dogs that match the search criteria, and then only returns the dogs that are on the desired page. This way, only the desired page is transferred to the browser. Using another column for sorting preserves the preference rank numbers. Filters reset to page 1, and the chart and map now reflect the current page. Their labels were changed to reflect this change.

Knowing exactly what was being measured made the performance trade-offs clearer. In a controlled experiment, 20,000 synthetic records were used to compare the exact search for animal type and breed, with and without an index on animal type, breed, and record ID. The record IDs being returned were unchanged; SQLite’s execution plan changed, from using the primary key index to using the multiple-column index. The medians of the recorded times were 0.2002ms and 0.0211ms, respectively. These are the times for one query pattern under the conditions of the experiment, and do not necessarily reflect a speedup that would be seen in production, nor do they take into account the cost of preference rank calculation.

The artifact successfully completes 61 automated tests, 19 of which are new tests for SQLite. They cover usage of real temporary databases for persistence, rollback, constraints, combined filters, sorting, paging, and error handling. Comparisons of SQL ranking against the previous Python algorithm are included for all three rescue profiles. Database administration commands and actual dashboard callback requests are also incorporated. For the local browser check, Water Rescue had 11 dogs returned; the second page still showed rank 11, and an unmatched breed resulted in a message for no results. The demo records are synthetic; the unavailable MongoDB database was not migrated and not tested.

The project achieves the database improvement goals set out in Outcomes Three, Four, and Five. Outcome Three is satisfied by the schema, query, indexing, and paging decisions. Outcome Four is achieved by the implementation of SQLAlchemy and SQLite and the integration tests that verify this. For Outcome Five, the implementation includes validated input, parameter handling, controlled errors, constraints, and transaction rollback. The README, comments, and this narrative satisfy Outcome Two. Outcome One's intention of documented interfaces and reproducible setup is met (although not actually achieved in practice by this milestone, since no collaboration with a real shelter team has occurred).

This enhancement reinforced the importance of considering failure cases when ensuring the correctness of a database. While ensuring the proper insertion of data was important, edge cases such as inserting duplicate records or records with missing information, or when an insert operation fails for a batch of data, were also important to have well-defined behavior. The importance of translating logic written in SQL and ensuring the results make sense was also highlighted. The tests that compare ranking ensure the ranking behavior implemented in Milestone Three is maintained despite the changes made to storage and paging. Short explanations for some of the decisions made, and edge cases handled, were added to comments.

My outcome coverage plan is unchanged from Module One, and I have now implemented the planned database changes for the local demonstration. Whilst SQLite is portable, a production deployment would require access controls, deployment effort, and testing for concurrent access. PostgreSQL is still to be tackled; the SQLite-specific constraints will need modification. The original remains available for comparison, and the augmented artifact now contains local setup and run instructions and test evidence. These additions to the application allow the database changes to be reviewed and demonstrate how storage choices impact the reliability and usability of the whole application.
