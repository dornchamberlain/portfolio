CS 499 Milestone Two Narrative

Dorn ChamberlainSeptember 20, 2026

Artifact and Purpose

For this milestone, I focused on improving the Animal Shelter Dashboard’s structure, maintainability, and reliability. The original application was written in Python and used JupyterDash, pandas, Plotly, Dash Leaflet, and MongoDB to visualize animal shelter records. The main files for the project are ProjectTwoDashboard.py and CRUD_Python_Module.py for the dashboard and the notebook version of the dashboard. The project is prior to this capstone project; the original Project Two README was created on February 22, 2026. February 22, 2026 documents the README’s creation date, rather than the creation dates of the source files.

The improvement in Milestone Two divides the dashboard into components with specific duties and allows the application to run outside of Jupyter. The original implementation of the rescue category filters, table, breed graph, and selected record map were carried over, with improvements to the configuration, validation, and error handling. This lays the foundation for improvements to the scoring algorithm and relational database implementation in later milestones.

Reasons for Inclusion and Improvements

This artifact combines interface development and back-end responsibilities into one application. This is interesting to me in regards to full stack software engineering and back-end engineering because the usefulness of the dashboard is contingent on the application's ability to reliably acquire, validate, and display information. The original design was a good opportunity to show growth, the dashboard was imported, it caused the database to be read, the credentials were written into the source code, and the map was reliant on the position of numeric columns.

The new version separates settings, repository access, record normalization, rescue rules, application services, layout, callbacks and visual design into different modules. The application factory creates a standard Dash app without loading animal records. The entry point runs the server only when directly executed. The dashboard service takes a repository dependency, enabling the same interface to be used with a MongoDB adapter or a JSON adapter with clearly labelled synthetic demonstration records. The dashboard only requires read access, which is why the new repository contract only supports reading records and closing resources. The full relational CRUD will form part of a later database enhancement.

The updates also fix individual issues noted during the code review. Incorrect configuration will cause an error message without any connection details to be shown. A failed source request will no longer be confused with a successful search with no results. Record normalization converts MongoDB IDs to stable strings, allows repeated animal IDs, and rejects missing or duplicate record IDs. The map will accept documents with named latitude/longitude fields, validate that they are in the correct range, and follow a selected record across potential table reordering. The interface will inform the user if their selected record has been deleted rather than unexpectedly showing them another animal. Records with missing, invalid, or negative ages do not satisfy the rescue filters. Zero remains allowed because the original rules did not specify a positive minimum age.

Course Outcomes and Coverage Plans

This enhancement achieves the intended software engineering goals for this milestone and is the best evidence of progress toward achieving Outcome Four - the use of computing techniques and tools to produce a maintainable solution. Progress toward this outcome is evidenced by a modular Python application, dependency injection, a standard Dash entry point, and automated tests. Progress towards Outcome Five - external configuration, field validation, limited data projection, safe database error messages, and separating the import function from resource access - is also evidenced by these changes. These were concrete security improvements, but they do not constitute a comprehensive production security review.

Design trade-offs such as stable record identity, validation behavior, and component boundaries' additional complexity were evaluated, and Outcome Three is supported. The application is still reading the entire record set and filtering in memory. This works well for the demonstration and MongoDB adapters, but it is costly in memory and for data transfer if record sets are large. This milestone supports Outcome Three through design trade-offs. Database pagination, scoring and ranking, and index evaluation remain future work.

Evidence for Outcomes One and Two includes documented interfaces, setup instructions, test results, and this explanation of the design. This is all that is needed to help another developer understand and assess the value of the project, so it is not directed at collaboration with a diverse team. My plan for coverage of the outcomes has not changed. The practical change is the addition of a runnable sample data mode and a read-only adapter boundary until the SQLAlchemy and SQLite work is complete.

Reflection on the Enhancement Process

This example demonstrates that separating files is beneficial only if it also separates responsibilities and dependencies. Simply moving the callback code would make it hard to test the database connection and data transformation. By defining the repository contract and moving normalization and filtering behind an application service, the interface was made explicit. Now the cost of having more files and interfaces to deal with is obvious, but the smaller surface area of each module is also apparent.

Fixed identity versus record identity: A row's position in a table may change depending on user sorting and filtering actions. An animal ID may be spread across multiple source records. A unique record ID was used to avoid any assumptions in map selection. Treatment of missing values: An unknown location needed to be explained, while unknown ages could not satisfy an age condition. In neither case was a value made up to keep a visualization functional.

A test revealed a framework integration issue that would not have been caught by isolated logic tests. The map component library was being imported only when a callback was first invoked. An HTTP callback test revealed that Dash did not like this late component library import. Moving the component imports to module initialization fixed the problem while preserving the requirement that importing the application must not access the database. This highlights the value of both unit tests and tests via the framework interface.

Verification and Remaining Work

The improved submission now passes 30 automated unittest tests written in Python 3.12, with dependency versions logged in requirements.txt. Tests include configuration, original rescue profiles, age bounds, record validation, duplicate identities, empty results, source failures, coordinate validation, stale selection, selection after reorder, and breed counts. It also includes Dash routes and callbacks (through the Flask test client). It also includes a subprocess check to ensure that importing the application does not create a MongoDB client. It was also run starting the application from outside of its own directory, to confirm that the packaged sample-data path was independent of the working directory.

These results confirm proper behavior of the sample data and mock database failure scenarios. It does not confirm connection to the original MongoDB data set, browser compatibility, production readiness, or database migration. The original source files were left unmodified and are provided separately for comparison purposes. Explainable candidate scoring and ranking will be the next feature to be implemented, followed by relational storage and integration tests. I will incorporate instructor feedback and examine coverage of remaining outcomes prior to the final ePortfolio publication.
