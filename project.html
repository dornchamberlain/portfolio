Animal Shelter Dashboard

For my capstone, I returned to my CS 340 dashboard to improve how the code is organized, how candidates are ranked, and how records are stored.

The starting point

The original CS 340 application used Python, JupyterDash, and MongoDB to filter shelter records and display a table, breed chart, and location map. Several responsibilities were combined in the same code, and connection settings were stored in the source. I wanted to make the application easier to understand, test, and maintain.

I no longer have access to the original database environment, so I used synthetic records to test the changes. The final application can run locally with SQLite.

How the final application works

The application checks the selected filters, retrieves the matching records, and updates the table, chart, and map. In SQLite mode, it scores and ranks all matching records before returning a page. This keeps a strong candidate from being overlooked just because it started on a later page, while limiting how much data is sent to the browser.

What I learned and what remains

Adding ranking made the results more informative, but it also required more processing and memory than the original filter. Returning one page at a time reduces the data sent to the browser, although the database still has to rank the matching records. The scores show preference matches; I have not validated them as a way to judge whether a dog is suitable for rescue work.

SQLite gave me a practical way to demonstrate reliable database operations locally. Before using this application in production, I would need to address user access, deployment, and testing with concurrent users. I also compared one query with and without an index using 20,000 synthetic records. That experiment shows the effect on that query, rather than a speed improvement for the entire application.
