Milestone Three Algorithms and Data Structures Narrative

Dorn Chamberlain

For Milestone Three, I enhanced the Animal Shelter Dashboard that I originally created for Project Two in CS 340, before beginning my CS 499 capstone. The original artifact includes a Python dashboard, a Jupyter Notebook version, and a CRUD module for MongoDB. It displays animal records in a table, summarizes breeds in a chart, and shows an animal's location on a map. During September 2026, I built on the modular version from Milestone Two by adding a scoring and ranking algorithm. The dashboard now shows how closely each dog matches the selected rescue role's preferences, along with an explanation of its score.

I selected this artifact because it gives me a practical way to connect backend logic with information a user can see and evaluate. The original rescue filters answered a yes-or-no question: did an animal meet every condition? That approach excluded partial matches without showing how close they were to the criteria. Ranking adds a different kind of information. A user can compare candidates and see which preferences contributed points. This makes the artifact useful for demonstrating algorithms and data structures in my ePortfolio, while continuing the same project across the capstone milestones.

The scoring profiles reuse the original breed and sex preferences and the existing age range of zero through 156 weeks. The example weights award 50 points for a preferred breed, 30 for an age within that range, and 20 for the preferred sex. A dog matching breed and age earns 80 points even if its sex does not match. Dogs remain candidates when they earn few or no points; cats and records with an unknown animal type are excluded from rescue ranking. These weights demonstrate a configurable algorithm. They have not been validated as a way to determine whether a dog is trained or ready for rescue work, and the dashboard explains that limitation.

The enhancement uses a dictionary to associate rescue roles with scoring profiles. Each profile keeps its preferences and weights together, and a frozenset stores its preferred breeds. A list holds the scored results, while each result dictionary contains the animal's fields, score, and explanation. Scoring and ranking are separate functions, which makes it easier to check individual point totals before checking the final ordering. Results are sorted by highest score first, then animal ID and unique record ID. That final distinction matters because one animal can have more than one record. Equal scores still receive separate rank positions, and the IDs make their order repeatable.

Handling incomplete information was an important design choice. Missing or invalid values earn zero points, and the remaining weights stay unchanged. Otherwise, a record with very little information could appear to have an unusually strong percentage score. The explanation distinguishes missing information from a known value that does not match a preference. Profile validation also rejects invalid weights, unusable preference names, and impossible age bounds. During the walkthrough, I checked why booleans need special handling in Python: True behaves like an integer, but it should not be accepted as a scoring weight or an animal's age.

I also considered the cost of ranking. For n records and m criteria, scoring takes O(nm) time under the assumption of bounded field lengths and average constant-time breed lookups. Sorting adds O(n log n) time. Keeping explanations uses O(nm) space, which becomes O(n) with the three fixed criteria. This adds work compared with the earlier filter, so I am not claiming a speed improvement. The benefit is a more informative result. The full candidate list is ranked before the table creates pages. Scoring only the first page could miss a better candidate later in the input, so the current design accepts the memory cost of processing the full list.

Testing helped me connect these decisions to observable behavior. I worked through small examples where I could calculate the expected scores, checked invalid profiles from the terminal, and added automated tests during the guided implementation. I also encountered an import error when my new function had not been saved, and a NameError when I had not imported the ranking function into the test file. Working through these errors reinforced the difference between code visible in the editor, code saved on disk, and names available inside a module. Establishing a central local Git repository gave me a baseline commit and a milestone-two tag before continuing the enhancement.

The completed artifact passes 42 automated tests. These cover the existing dashboard behavior as well as scoring totals, age boundaries, missing data, invalid settings, consistent ties, and a top candidate located beyond the first page of input. In the browser, I checked ranked results and their explanations. Reset returned all 12 synthetic records, including the cat, with blank ranking fields. The completed callback also clears the previous table sort when the rescue category changes so the new ranking can appear in its intended order. The tests and demonstration use synthetic records and mocked database access; they do not establish that a live MongoDB deployment has been tested.

This enhancement meets the goals I planned for Course Outcome Three by applying algorithmic principles and explaining trade-offs involving data structures, incomplete information, ordering, and memory use. It supports Outcome Four through a working Python implementation with automated tests and dashboard integration. The explanations, README, and narrative support Outcome Two by communicating the results and design choices. Validating profiles and incoming records contributes to Outcome Five's security mindset by reducing the chance that invalid input will produce misleading results. The documented interfaces and understandable scores also support the intent of Outcome One, although I have not evaluated the dashboard with an actual shelter team.

My outcome-coverage plan remains the same. This milestone focuses on algorithms and data structures, while the SQLAlchemy and SQLite migration remains part of the later database enhancement. The main lesson from this work is that a useful ranking needs more than a correct total. It also needs clear assumptions, predictable ties, sensible treatment of missing data, and an explanation a user can follow. Working through the code and tests step by step helped me understand those choices. I also revised comments and documentation to explain them in my own words. Together, these changes make the artifact a stronger example of the backend problem solving I want to demonstrate in my ePortfolio.
